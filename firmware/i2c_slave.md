# I2C slave interface

The firmware exposes `I2C0` as a 7-bit I2C slave at address `0x2A`. It is a
small read-mostly status interface, not a general-purpose register file.

## Electrical configuration

| Signal | CC1310 pin | Configuration |
| --- | --- | --- |
| SCL | DIO16 | input enabled, internal pull-up, open drain, `PIN_DRVSTR_MIN` (2 mA) |
| SDA | DIO17 | input enabled, internal pull-up, open drain, `PIN_DRVSTR_MIN` (2 mA) |

The pins are 3.3 V-only and must never be connected to 5 V. The CC1310 has an
internal pull-up enable, but not a selectable strong-pull-up mode. Since this
board has no external pull-ups, use a short, low-capacitance bus. The slave
does not select an I2C rate: SCL is generated by the master. The paired test
firmware uses 50 kHz; external pull-ups are required before increasing bus
length, capacitance, or clock rate.

> clock and needs no frequency-setting change of its own.

DIO16 and DIO17 are also the board's TDO/TDI aliases. The project uses cJTAG,
which does not require these pins, so this I2C assignment does not prevent a
cJTAG connection.

## Ownership and execution model

The TI `I2C` driver supports master mode only, so this implementation owns
I2C0 through driverlib. Its interrupt is installed with a SYS/BIOS `Hwi` on
`INT_I2C_IRQ`; no other code may open `Board_I2C0`. In particular, it must not
use driverlib `I2CIntRegister()`, because that function replaces VTOR while
SYS/BIOS and the RF stack share the application's vector table.

The I2C interrupt handler receives the pointer and write payload, supplies
read bytes to `I2CSlaveDataPut()`, and, when dump is enabled, captures the
bytes actually supplied during a read. A completed payload/dump record is
placed in one pending slot and a semaphore posts the worker.

The detached `i2c_slave` pthread has priority 1 and a 1024-byte stack. It
validates commands, updates the published status bank, and prints optional
UART dump lines. It does not perform UART output from the I2C ISR.

There is exactly one pending record. A new completed write with a payload, or
a dump-enabled read, arriving while that record is still pending is not handed
to the worker and increments `errorCount`. This does not turn an already ACKed
I2C transfer into a bus error. Hosts that correlate `ipc dump` output should
wait for the matching line before starting the next transaction.

## Transactions and addressing

The first write byte is always the 8-bit register pointer. A write payload is
all following bytes.

```text
write: START + 0x2A(W) + pointer + payload + STOP
read:  START + 0x2A(W) + pointer + REPEATED START + 0x2A(R) + data + STOP
```

A pointer-only write is valid and is normally used as the first part of a
read. It creates no worker record and does not increment `transactionCount`.

The CC1310 master scan implementation probes an address with
`START + address(R) + one-byte receive + STOP`; it cannot issue an address-only
probe. If this slave receives such a read without a preceding pointer, it ACKs
and returns a fixed zero byte. It neither advances the saved register pointer
nor emits an `ipc read` line, so scans cannot be mistaken for register reads.

The status area is physically 64 bytes. For reads, each byte is indexed with
`pointer & 0x3f`, and the pointer advances after each supplied byte. Thus the
read address wraps every 64 bytes: `0xC8` reads offset `0x08`. A read snapshots
which of the two published status banks to use when it receives the pointer;
all bytes in that read come from that same bank even if the worker publishes a
new bank concurrently.

A write payload is buffered up to 64 bytes. Bytes after the first 64 are
discarded and each discarded byte increments `errorCount`. Apart from the
command below, a non-empty write is protocol-invalid: it is accepted on the
bus, then the worker increments `errorCount`; it never modifies the status
bank.

## Status map

All multi-byte fields are little-endian. Bytes not listed below read as zero.

| Offset | Size | Value |
| --- | ---: | --- |
| `0x00` | 4 | ASCII magic `I2CS` |
| `0x04` | 1 | Interface version, currently `1` |
| `0x05` | 4 | Firmware version code `0x00MMmmpp` |
| `0x09` | 1 | Role: `1=rx`, `2=tx` |
| `0x0A` | 4 | `transactionCount`: completed writes with at least one payload byte that were queued to the worker |
| `0x0E` | 4 | `errorCount` |
| `0x12` | 4 | `Clock_getTicks()` value at the last status-bank publication |

The command mailbox is selected by the full pointer value `0x40`, even though
normal reads wrap at 64 bytes:

```text
START + 0x2A(W) + 0x40 + 0x01 + STOP
```

When that exact one-byte payload reaches the worker, it clears
`transactionCount` and `errorCount`, then publishes a new status bank. Any
other non-empty write increments `errorCount`. There is intentionally no I2C
operation to change role, reset the device, write Flash, or enter the
bootloader.

## UART transaction dump

Dumping is disabled by default. Enable or disable it through the common CLI:

```text
ipc dump on
ipc dump off
```

With dumping enabled, completed payload writes and reads produce lines such as:

```text
OK ipc write reg=0x80 len=3 data=010203
OK ipc read reg=0x00 len=4 data=49324353
```

For a write, `data` is the payload after the pointer. For a read, the ISR saves
the exact ordered values supplied to `I2CSlaveDataPut()` and the worker prints
that capture after STOP; it is not a later reread of dynamic status fields.
The output `reg` is the received pointer for a read or write. At most 64 data
bytes are represented. Dumping does not otherwise alter the I2C protocol or
status map; see [`cli.md`](cli.md) for the CLI response contract.
